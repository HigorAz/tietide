## Executive summary

Consolidated 63 verified findings into 40 deduplicated tracker entries spanning the full TieTide platform. Severity profile after de-dup and verifier-driven re-grading: 1 CRITICAL (Code-node sandbox escape → RCE + cross-tenant secret exfiltration), 3 HIGH (HTTP-request redirect SSRF bypass — the single most-reported bug, merged from 4 dimensions; and two org-scoping IDOR leaks in workflow versions/documentation), ~12 MEDIUM, ~16 LOW, ~8 IMPROVEMENT. Headline risks: (1) the worker Code node is a full sandbox escape giving any authenticated tenant RCE and access to ENCRYPTION_MASTER_KEY (decrypts every tenant's secrets); (2) the SSRF guard is bypassable via HTTP redirects and IPv4-mapped IPv6 literals, reaching cloud metadata/internal services; (3) workflow version & documentation endpoints still authorize by author userId instead of organizationId, leaking full definitions to ejected ex-members. Several documented security controls (per-route throttle env knobs, triggerData 64 KiB cap, audit completeness, SSRF DNS-pin/redirect re-validation) are claimed as delivered but absent in code — regressed/false-fixed. Recurring structural themes: count-then-create TOCTOU on every plan-limit check, public webhook endpoints fully exempt from throttling, and missing engine-level execution timeouts enabling cross-tenant worker starvation.

## CRITICAL

- [ ] **W5.1** (CRITICAL / security) — Code node sandbox escape → RCE + full secret exfiltration via host Object constructor  
       _Dimension_: Code Sandbox & SSRF  
       _Location_: `apps/worker/src/nodes/actions/code.ts:35-95 (WORKER_SOURCE host intrinsic bindings + vm.runInContext); test gap: apps/worker/src/nodes/actions/code.spec.ts:242`  
       The Code action injects the worker realm's own built-in constructors (Object, Error, Array, Promise, Map, Set) directly into the vm context. `codeGeneration:{strings:false}` only disables eval/Function for code originating INSIDE the context — it does not neuter the host Function constructor reachable via `Object.constructor`. User code runs `Object.constructor('return process')()` to obtain the real host process, then `process.env.ENCRYPTION_MASTER_KEY` (decrypts every tenant's Secrets/Connections), `DATABASE_URL`, `JWT_SECRET`, `WEBHOOK_HMAC_SECRET`, all OAuth secrets, and `process.getBuiltinModule('child_process').execSync(...)` for arbitrary OS command execution. Empirically reproduced against the exact vm setup. The Code node is registered as a normal action runnable by any authenticated user via POST /v1/workflows/:id/execute with no role gate, so this is authenticated-tenant RCE on the worker plus cross-tenant secret decryption. The existing test only checks bare typeof require/process/global are undefined and never probes Object.constructor. Fix: run user code in a true isolate — bootstrap built-ins INSIDE the context via vm.runInContext (so codeGeneration:false governs their Function constructor) or switch to isolated-vm; additionally pass an explicit minimal `env` to the Worker so even a partial escape cannot read master keys; add a regression test asserting Object.constructor('return process')() throws/returns undefined.  
       **Fix**: Do not pass host intrinsics into the vm context — create built-ins inside the sandboxed realm via a bootstrap vm.runInContext script, or migrate to isolated-vm for a separate V8 isolate. Scrub the worker's process.env before spawn (pass `env:` allowlist to the Worker). Add a regression test for the Object.constructor escape.

## HIGH

- [ ] **W5.2** (HIGH / security) — HTTP Request node follows redirects with no SSRF re-validation — guard bypass to cloud metadata / internal services  
       _Dimension_: Code Sandbox & SSRF / Workflow Engine / Provider Integrations / Encryption & Secrets  
       _Location_: `apps/worker/src/nodes/actions/http-request.ts:76-89 (+ ssrf-guard.ts:97-144); test gap: http-request.spec.ts has no redirect coverage`  
       Merged from ENC-1, SSRF-1, WE-1, PI-1 — one root cause reported across four dimensions. assertUrlAllowed() validates only the initial user-supplied URL (line 76), then fetch() is called with no `redirect` option, so undici defaults to `redirect:'follow'` (up to 20 hops). An attacker-controlled public host returns 302 Location: http://169.254.169.254/latest/meta-data/iam/security-credentials/ (or 127.0.0.1, the AI service, Postgres/Valkey, localhost admin); the SSRF guard never re-runs on the redirect target, and the internal/metadata response body is captured into ExecutionStep.outputData and readable via GET /v1/executions/:id/steps. This fully defeats the guard for any non-literal-IP target. Reachable by any authenticated workflow author. Notably the audit tracker (SECURITY-QA-AUDIT.md:49-50, W1.5) marks 'redirect re-validation' as delivered — it is absent, so this is a regressed/false-fixed finding. Connection-injected Authorization is stripped on cross-origin redirects, but the core internal-read primitive needs no credential. Fix: set `redirect:'manual'`, re-run assertUrlAllowed on every Location before following with a small hop cap (<=5), or use a custom undici dispatcher that pins the validated IP on connect; add a spec asserting a 302 to a private/metadata IP is blocked.  
       **Fix**: Pass `redirect:'manual'` to fetch and re-validate each Location via assertUrlAllowed before following (bounded hop count), or pin the validated IP into the socket connect with a custom undici dispatcher. Add a redirect-to-private-IP regression test.

- [ ] **W5.3** (HIGH / security) — IPv4-mapped IPv6 literals in hex form bypass the SSRF guard (::ffff:127.0.0.1 → ::ffff:7f00:1)  
       _Dimension_: Code Sandbox & SSRF  
       _Location_: `apps/worker/src/nodes/actions/ssrf-guard.ts:73-84 (isBlockedV6 mapped regex) and :114-122 (literal-IP path)`  
       isBlockedV6 only recognizes IPv4-mapped addresses in dotted-decimal form (/^::ffff:(\d+\.\d+\.\d+\.\d+)$/). The WHATWG URL parser normalizes http://[::ffff:127.0.0.1]/ to the hex form ::ffff:7f00:1, which the regex misses and which falls through every other branch → returns false → request allowed. Empirically confirmed that ::ffff:7f00:1 (loopback), ::ffff:a00:1 (10.0.0.1 RFC1918), and ::ffff:a9fe:a9fe (169.254.169.254 cloud metadata) all bypass, and that undici/net.connect route these to the real IPv4 targets and return internal data. The same gap applies when DNS resolution returns an IPv4-mapped address in hex form; NAT64 64:ff9b::/96 is also unblocked. Any authenticated user can exfiltrate cloud IAM credentials or reach loopback/RFC1918 internal services (postgres, valkey, AI service) with a one-line literal URL. Fix: in isBlockedV6, after lowercasing, parse the hex IPv4-mapped form (/^::ffff:([0-9a-f]{1,4}):([0-9a-f]{1,4})$/), reconstruct the embedded v4 address, and run isBlockedV4 on it; better, normalize any v6 to canonical bytes via ipaddr.js and classify on integer ranges. Add specs for ::ffff:7f00:1, ::ffff:a00:1, ::ffff:a9fe:a9fe, and 64:ff9b::7f00:1.  
       **Fix**: Parse the hex IPv4-mapped IPv6 form and run isBlockedV4 on the embedded address; ideally normalize all IPv6 to canonical bytes (ipaddr.js) and classify by integer range. Block NAT64 64:ff9b::/96. Add regression specs for the hex forms.

Correct the audit tracker.  
       **Fix**: Resolve and validate once, then pin the validated IP into the socket via a custom undici dispatcher/lookup (Host/SNI kept as the original hostname). Re-open W1.5 in the tracker since DNS-pin was never implemented.

- [ ] **W5.9** (MEDIUM / security) — Login rate-limit bucket folds in the email, removing any per-IP cap — enables single-IP password spraying  
       _Dimension_: Auth & Session

- [ ] **W5.10** (MEDIUM / security) — Public webhook & provider-webhook endpoints fully @SkipThrottle — unauthenticated unbounded DB load before any signature check  
       _Dimension_: Webhooks & Signatures / Rate Limiting & DoS  
       _Location_: `apps/api/src/webhooks/webhooks.controller.ts:20; apps/api/src/provider-webhooks/provider-webhooks.controller.ts:31; apps/api/src/webhooks/webhooks.service.ts:38-49`  
       Merged from WS-1 and RL-3. Both inbound webhook controllers carry class-level @SkipThrottle(), so the global TieTideThrottlerGuard never rate-limits POST /v1/webhooks/:path or POST /v1/provider-webhooks/:provider/:subscriptionId. - [ ] **W5.12** (MEDIUM / security) — Inline getConnection/refreshConnection ignore connection status and lockout counter — self-inflicted bad-token loop against OAuth provider  
       _Dimension_: Provider Integrations  
       _Location_: `apps/worker/src/connections/prisma-connection-resolver.ts:35-63 and 84-141`  
       getConnection() filters only by id+organizationId and never checks status; refreshConnection() refreshes regardless of refreshFailureCount. The background processor enforces a MAX_REFRESH_FAILURES lockout (sets status=EXPIRED), and the background refresh scanner only scans status=ACTIVE — but the inline execution path honors neither. A connection the system has already locked out (EXPIRED, revoked refresh token) is still loaded and used on every workflow run, and on each auth error the inline path re-hits the provider token endpoint with the known-bad token. For a cron/poll-scheduled workflow this repeats every tick indefinitely with no backoff — a self-inflicted bad-token loop that wastes provider quota and can get the platform's shared OAuth client throttled/flagged. No auth/data boundary is crossed (org-scoped, tokens not leaked), so verifiers downgraded toward LOW; recorded as MEDIUM/LOW operational-abuse. Fix: in getConnection reject/skip inline refresh for EXPIRED connections; in refreshConnection short-circuit when refreshFailureCount >= MAX_REFRESH_FAILURES with a ConnectionAuthError; add an exponential-backoff / lastRefreshAttemptAt gate.  
       **Fix**: Honor connection status and refreshFailureCount on the inline path: skip EXPIRED connections, short-circuit refresh at the failure cap, and add a backoff gate.

- [ ] **W5.13** (MEDIUM / correctness) — Successful refresh followed by a non-auth provider error marks a healthy connection EXPIRED  
       _Dimension_: Provider Integrations  
       _Location_: `packages/sdk/src/base/connector-action.ts:84-118`  
       On the first auth error the action refreshes the token and retries run(). If that retry throws a NON-auth error (provider 500, downstream timeout, node bug), the catch calls context.markConnectionForRefresh(connectionId), which unconditionally sets status=EXPIRED and increments refreshFailureCount. So a transient provider 5xx right after a perfectly good token refresh disables a connection whose credentials are valid and contributes toward the lockout counter, causing spurious 'reconnect your account' churn. The disable is sticky (the background scanner only scans ACTIVE, so it is never auto-recovered) and contradicts the codebase's own grading convention elsewhere (a single failure → ERROR, EXPIRED reserved for the failure cap). Recoverable by reconnect (no data loss, not attacker-driven), so verifiers split MEDIUM/LOW. Fix: only mark-for-refresh on auth errors — in the non-auth retry-failure branch, rethrow the error WITHOUT calling markConnectionForRefresh.  
       **Fix**: In the post-refresh retry catch, rethrow non-auth errors without calling markConnectionForRefresh; only auth errors are evidence the credential is bad.

- [ ] **W5.14** (MEDIUM / efficiency) — SQL rowLimit applied in-process AFTER the full result set is materialized → worker OOM  
       _Dimension_: Provider Integrations  
       _Location_: `apps/worker/src/nodes/connectors/postgres/postgres-client.factory.ts:64-69; apps/worker/src/nodes/connectors/mysql/mysql-client.factory.ts:61-67`  
       The query text is sent to the DB with NO server-side LIMIT; pool.query/pool.execute fetches the ENTIRE result set into memory and only then applies rows.slice(0, rowLimit). The schema comment claims rowLimit 'limits memory exhaustion vectors' but the cap runs after materialization. A query like SELECT _ FROM big_table (which passes the schema's comment/semicolon/interpolation checks) pulls millions of rows into the shared worker heap, OOM-killing the worker process (concurrency=5) and aborting all tenants' in-flight executions. rowCount is also reported pre-slice, misleading downstream nodes. Self-inflicted by the authenticated workflow author against their own DB (no cross-tenant read), so it is an availability/efficiency issue. Fix: enforce the cap at the DB layer — wrap as `SELECT _ FROM (<query>) \_t LIMIT $n` or use a streaming cursor (pg-cursor / mysql2 stream) that stops after rowLimit rows; do not slice after the fact; correct the schema comment.  
       **Fix**: Push the row cap into the DB via a wrapping LIMIT or a streaming cursor that halts at rowLimit; report rowCount post-cap; fix the misleading schema comment.

- [ ] **W5.15** (MEDIUM / efficiency) — No per-node or per-execution timeout in the engine — a single run can occupy a worker slot indefinitely (cross-tenant starvation)  
       _Dimension_: Workflow Engine  
       _Location_: `apps/worker/src/engine/workflow-runner.ts:159-415; apps/worker/src/processors/workflow.processor.ts:19`  
       The runner awaits each node's executor with no wall-clock budget and no engine-enforced per-node timeout, and the BullMQ processor sets no job timeout (BullMQ has none built in). Only http-request (30s) and code (<=30s) self-impose limits; database connectors set only connectTimeout (no statement_timeout/query_timeout), so SELECT pg_sleep(3600) / SELECT SLEEP(3600) blocks the slot for the full duration. With worker concurrency=5 on a single shared queue, five such concurrent runs starve the worker and queue all other tenants' executions indefinitely. Reachable by any authenticated user; availability-only impact. Fix: add an engine-level per-node timeout (wrap executor.execute in Promise.race with a configurable default, e.g. 60s) and an overall per-execution wall-clock cap; set DB-layer statement timeouts; configure BullMQ lockDuration/maxStalledCount and propagate an AbortSignal into connectors that support it.  
       **Fix**: Enforce a configurable per-node timeout (Promise.race) and an overall per-execution deadline in the engine; set statement_timeout on DB connectors and propagate AbortSignal where supported.

- [ ] **W5.16** (MEDIUM / correctness) — Unbounded node count plus nested iterator/subworkflow fan-out enables resource-exhaustion DoS  
       _Dimension_: Workflow Engine  
       _Location_: `packages/shared/src/schemas/workflow.schema.ts:95-101; apps/worker/src/engine/workflow-runner.ts:283; iterator-executor.ts; subworkflow.ts`

- [ ] **W5.17** (MEDIUM / correctness) — Stripe webhook has no event-id dedup or out-of-order guard — a retried subscription.updated can resurrect a cancelled paid plan  
       _Dimension_: Billing & Entitlements
